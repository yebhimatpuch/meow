# 1. FTK Imager

**Core Purpose:** FTK Imager is a data preview and imaging tool used to acquire data (triage and imaging) in a forensically sound manner without altering the original evidence.

### **1. Evidence Acquisition (Creating Disk Images)**

- **The Process:** `File` -> `Create Disk Image`.
- **Source Selection (Crucial Viva Concept):**
    - **Physical Drive:** Captures the *entire* storage medium bit-by-bit, including all partitions, unallocated space, and slack space. This is the gold standard for full forensic investigations.
    - **Logical Drive:** Captures only a specific partition (e.g., `C:\` drive) or specific files. It does not capture unallocated space outside that partition.
- **Case Information:** Always fill out the evidence item information (Case Number, Evidence Number, Examiner Name). *Lab Evaluation Note: This is mandatory for maintaining the Chain of Custody.*
- **Verification:** Always check "Verify images after creation." This computes the MD5 and SHA-1 hashes of the original drive and compares them to the generated image to prove the data was not altered during acquisition.

### **2. Image Formats**

- **RAW (`.dd`):** A flat, bit-by-bit copy. It contains raw data with no compression and minimal metadata. Universally supported by almost all Linux and Windows forensic tools.
- **E01 (EnCase Evidence File):** The industry standard. It compresses data, supports encryption, and embeds the case metadata and hashes directly into the file structure.
- **AFF (Advanced Forensic Format):** An open-source format that also stores data and metadata together, heavily used in open-source forensic tools.
- **SMART:** Originally designed for Linux, it is another format that includes metadata and supports compression.

### **3. Image Analysis & Navigation**

- **Loading Evidence:** `File` -> `Add Evidence Item` -> Select the generated image file.
- **Log File:** Along with the image, FTK generates a `.txt` summary file containing drive geometry, sector counts, and the vital acquisition hashes.
- **Evidence Tree:** Data is explored via the tree on the left. You can expand the `root` directory to view the active file system.
- **Deleted Files:** Indicated by a red **"X"** over the file icon. FTK Imager can recover some deleted files if their metadata (like MFT entries in NTFS) is still intact, though dedicated carving tools are better for deeply buried data.

### **4. Exporting & Reporting**

- **Export Hash List:** Generates a `.csv` containing the MD5/SHA-1 hashes of every file in the image.
    - *Lab Use Case:* You can run these hashes against databases like VirusTotal to quickly identify malware, or against the NSRL (National Software Reference Library) to filter out known, safe OS system files (whitelisting).
- **Directory Listing:** Exports a `.csv` detailing file paths, MAC times (Modified, Accessed, Created dates), and whether the file is marked as deleted.

### **5. Advanced Capabilities**

- **Memory Capture:** `File` -> `Capture Memory`. Allows you to dump live RAM (creating a `.mem` or `.raw` file) and capture the Windows `pagefile.sys`. This is critical for catching active malware or encryption keys before the system is powered off.
- **Decryption:** Can mount and decrypt files, provided you have the recovery keys or passwords (e.g., BitLocker recovery keys).

### **6. File System & Hex Analysis (The "Byte Structure")**

- **Boot Signatures:** In the hex viewer, looking at partition tables (like FAT1/FAT2), the end of a boot sector (sector 512) is always marked by the hex signature **`55 AA`**.
- **Unallocated Space:** This area is not actively mapped by the file system but contains remnants of deleted files.
- **File Signatures (Magic Numbers):** When analyzing unallocated space, you identify file types by their byte structure (headers) rather than their extensions. For example, a JPEG will always start with `FF D8 FF E0`.

# **2. Linux Acquisition Tools (Guymager, dd, dc3dd)**

**Pre-Acquisition Phase (Crucial Lab Step)**

- `sudo fdisk -l`: Lists all partition tables and storage devices.
- `lsblk`: A must-know alternative. It outputs a much cleaner, tree-like view of block devices and their mount points.
- **Golden Rule:** Ensure your evidence drive is **read-only** or at least completely unmounted before acquisition to prevent accidental writes.

### **Guymager (The Linux GUI Standard)**

While it has a GUI, it is extremely powerful and purpose-built for forensics.

- **Execution:** Always run as root (`sudo guymager`).
- **Why use it?** It is multi-threaded, making it incredibly fast. It natively supports creating EnCase (`.E01`, `.Ex01`) and AFF formats, not just raw images.
- **Lab Tip:** In the GUI, always check the boxes for computing both MD5 and SHA-256 hashes simultaneously. It embeds these hashes and the log files directly into the metadata if you choose the `.E01` format.

### **`dd` (Data Definition / "Disk Destroyer")**

`dd` is a low-level, bit-by-bit copying utility present on almost all Unix systems. It is completely blind to file systems; it just reads and writes zeros and ones.

**The Master Command:**

`sudo dd if=/dev/sdb of=/path/to/evidence.dd bs=4096 conv=noerror,sync status=progress`

**Deconstructing the Flags (Viva Essentials):**

- `if=` (Input File): The source. **Warning:** Reversing `if` and `of` will overwrite your evidence drive. Double-check this every time.
- `of=` (Output File): The destination image file.
- `bs=4096` (Block Size): Determines how much data is read/written at a time. `bs=512` is the sector size of older disks, but `bs=4096` or `bs=64K` drastically speeds up the process on modern hardware.
- `conv=noerror,sync` (The Forensic Lifesaver):
    - `noerror`: If `dd` hits a physically bad sector on a damaged drive, it won't crash and abort the whole image.
    - `sync`: If a bad sector is skipped, `sync` pads the output file with zeros for that sector. This ensures the byte alignment of the rest of the image remains perfect. Without it, the whole file system would shift and become unreadable.
- `status=progress`: A must-know addon. Native `dd` operates silently. This flag gives you a real-time progress bar and speed metric.

### **`dc3dd` (The Forensic Upgrade)**

Developed by the Defense Cyber Crime Center (DC3), this is a patched version of `dd` explicitly designed to fix `dd`'s forensic shortcomings (like silent operation and lack of native hashing).

**Use Case 1: Standard Acquisition with On-the-Fly Hashing**

`sudo dc3dd if=/dev/sdb of=evidence.dd hash=md5 hash=sha256 log=acquisition_log.txt`

- *Advantage:* Instead of running `dd` and then running a separate `md5sum` command (which reads the whole massive file twice), `dc3dd` hashes the data stream as it copies, cutting acquisition time in half.
- *Addon:* You can specify multiple hash algorithms simultaneously.

**Use Case 2: Handling Large Drives (Splitting)**

Bash

`sudo dc3dd if=/dev/sdb ofs=image_split.000 ofsz=2G log=split_log.txt hash=sha1`

- *Why?* If you are saving the image to an external drive formatted in FAT32, it cannot hold a file larger than 4GB.
- *Flags:* `ofs` designates a split output file, and `ofsz` sets the size limit per chunk (e.g., 2 Gigabytes).
- *Reassembly:* To merge them back later for analysis: `cat image_split.0* > merged_image.dd`

**Use Case 3: Drive Sanitization (Wiping)**

Before you write an image to a destination drive, that destination must be forensically wiped (zeroed out) so no old data bleeds into your investigation.

Bash

`sudo dc3dd wipe=/dev/sdc pat=00`

- *Flags:* `wipe` targets the drive. `pat=00` writes zeros across the entire disk. You can use `pat=FF` to write ones, or `tpat` for text patterns.

# **Command Line Acquisition & Carving**

### **1. Live System Data Extraction (The `/proc` Directory)**

The `/proc` directory is a virtual file system in Linux. It doesn't contain actual files on a hard drive; it contains real-time kernel and system information. Using `dd` to read these is a form of **live forensics**.

- **`sudo dd if=/proc/kcore | hexdump -C | less`**
    - `/proc/kcore` represents the system's **physical RAM** (memory), not just swap. It's an ELF core format representation of memory.
    - *Command breakdown:* We pipe (`|`) the raw memory dump into `hexdump -C` to format it into readable hexadecimal and ASCII columns, and then into `less` so we can scroll through it without crashing the terminal.
- **`sudo dd if=/proc/interrupts`**: Records the number of interrupts per IRQ (hardware communications). Useful to see if a hidden device (like a hardware keylogger) is heavily communicating.
- **`sudo dd if=/proc/uptime`**: Shows how long the system has been running. Crucial for establishing a timeline.
- **`sudo dd if=/proc/partitions`**: Lists all partition blocks currently recognized by the kernel.
- **`sudo dd if=/proc/meminfo`**: Gives a human-readable summary of RAM and Swap usage.
- **`sudo dd if=/proc/kallsyms`**: Lists all exported kernel symbols. Used in advanced memory forensics to detect rootkits hooking into the kernel.

### **2. Handling Failing or Faulty Drives (`dd` vs. `ddrescue`)**

When a drive is physically clicking or dying, standard imaging tools will freeze or crash.

**Using `dd` for failing drives:**

- `sudo dd if=/dev/sdc of=output.img conv=noerror,sync bs=4M status=progress`
    - **`conv=noerror`**: Instructs `dd` to *not* stop when it hits a read error (bad sector).
    - **`sync`**: Pads the unreadable sectors with null bytes (zeros) in the output image. This ensures the data offsets remain perfectly aligned.
    - **`bs=4M`**: Sets the Block Size. Reading in 4 Megabyte chunks is vastly faster than the default 512 bytes.
    - **`status=progress`**: Without this, `dd` sits silently. This shows you the transfer speed and bytes copied.

**Using `ddrescue` (The Superior Choice for Faulty Drives):**

> **Why `ddrescue` is better than `dd` ?**
*⇒ " ddrescue reads the good blocks first to secure the bulk of the data safely, and only then goes back to scrape the bad sectors. It also uses a log/map file so if the drive dies and restarts, you don't lose your progress."*
> 
- **`sudo dmesg`**: Displays the kernel ring buffer. *Why it matters:* If you plug in a corrupted USB, run `dmesg | tail`. It will print out the exact hardware errors and tell you the assigned device ID (e.g., `sdb`, `sdc`).
- **`sudo fsck`**: File System Consistency Check.
    - 🚨 **MAJOR VIVA TRAP:** *Never* run `fsck` on original evidence! It writes to the disk to "fix" it, which destroys the forensic integrity. Only run it on a *copy* of your image if you are trying to mount a corrupted file system.
        
        <aside>
        💡
        
        You cannot run `fsck` directly on a `.raw` or `.dd` file. You must first trick Linux into treating the file like a physical drive using a "loop device."
        
        **🚨 Golden Rule Reminder:** ONLY do this on a **copy** of your image! `fsck` alters data to fix errors, which destroys forensic integrity.
        
        Here is the exact, super-short workflow for your lab:
        
        **1. Attach the image as a loop device:**
        
        `sudo losetup -fP my_copied_image.raw`
        
        **2. Find out what name it was given:**
        
        `lsblk`
        
        *(Look for your loop device, it will likely be named something like `/dev/loop0` with a partition under it like `/dev/loop0p1`).*
        
        **3. Run `fsck` on that specific partition:**
        
        `sudo fsck -y /dev/loop0p1`
        
        **4. Detach when finished:**
        
        `sudo losetup -d /dev/loop0`
        
        ### **Essential `fsck` Input Parameters (Flags)**
        
        Yes, it has crucial flags you need to know:
        
        - **`y`**: Automatically answers "yes" to all repair prompts. (Use this in the lab to quickly fix your copy and mount it).
        - **`n`**: Dry run. It checks for errors but answers "no" to everything, making **zero changes**. (The safest way to just *see* the damage).
        - **`f`**: Forces a check even if the OS thinks the file system is perfectly clean.
        </aside>
        
- **`sudo ddrescue -d -r5 /dev/sdb mydrive1.raw mydrive1.log`**
    - **`d`**: Direct access. Bypasses the kernel cache directly to the hardware.
    - **`r5`**: Retries bad sectors 5 times before giving up.
    - **`mydrive1.log`**: The map/log file. This is mandatory. It tracks which sectors were copied successfully and which failed.
    - **`b 4096`**: *(Optional)* Forces the sector size (e.g., 4096 bytes for modern Advanced Format drives) instead of letting the tool guess.

### **3. Basic Disk Forensics**

- **`df -h` (Disk Free):** Shows the amount of available and used disk space on mounted file systems. The `h` flag makes it "human-readable" (Megabytes/Gigabytes instead of bytes).
- **`du -h` (Disk Usage):** Recursively details how much space specific files and directories are taking up. Useful for finding massive hidden files (like encrypted containers).

### **4. File Carving (Extracting Data without a File System)**

Carving ignores the Master File Table (MFT) or FAT. It searches the raw, raw 1s and 0s for "Magic Numbers" (File Headers and Footers) to extract files from unallocated space or formatted drives.

**Foremost:**

- **The Config File (`/etc/foremost.conf`):** This is the brain of Foremost. By default, it searches for a few standard things. You use a text editor (`sudo nano /etc/foremost.conf`) to uncomment (remove the `#`) lines for the specific file types you are hunting, or add custom hex signatures.
- **`sudo foremost -i mydrive.raw -o foremost_folder1 -v -t png,pdf`**
    - **`i`**: Input (your raw image file).
    - **`o`**: Output directory. *Note: Foremost requires the output directory to be completely empty or non-existent prior to running.*
    - **`v`**: Verbose. Prints what it is finding to the screen in real-time.
    - **`t`**: Filters extraction by type (e.g., `png,pdf,zip`).
- **`audit.txt`:** Inside your output folder, Foremost creates an audit log. This proves exactly from which byte offset a specific file was carved. Highly important for reporting.

**Recoverjpeg:**

- **`recoverjpeg image1.dd -o recoverjpeg_folder`**
    - A hyper-specialized carver. While Foremost does everything, `recoverjpeg` only looks for the `FF D8 FF E0` hex signatures of JPEGs. It is often faster and yields fewer false positives when you *only* need pictures.

# **Advanced Carving & Extraction Tools**

**Scalpel (The Optimized File Carver)**

*Viva Tip: If the examiner asks, "Why use Scalpel when Foremost exists?" Your answer should be: "Scalpel is actually a total rewrite of Foremost. It is highly optimized, uses significantly less RAM, and is usually much faster when carving large disk images."*

- **The Configuration File:**
    - Edit it using a text editor: `sudo nano /etc/scalpel/scalpel.conf` (the exact path can vary slightly between Linux distributions, sometimes just `/etc/scalpel.conf`).
    - Like Foremost, Scalpel will do absolutely nothing until you open this file and "uncomment" (remove the `#`) the specific file types you want to carve (e.g., JPEG, PDF, DOC).
- **The Command:**
    - `sudo scalpel -c /etc/scalpel/scalpel.conf -o out_folder image1.dd`
    - **`c`**: Points to the configuration file. (If you don't use this flag, Scalpel usually looks in the default `/etc` directory anyway, but it is best practice to specify it in a lab).
    - **`o`**: The output folder. **Crucial Rule:** Just like Foremost, this folder *must not exist* before you run the command. Scalpel will create it. If the folder already exists, the tool will throw an error and quit.

### **Bulk Extractor (The Pattern Hunter)**

*Viva Tip: This is a major trap! Bulk Extractor is **not** a traditional file carver like Foremost or Scalpel. It does not extract whole files (like a `.jpg`). Instead, it extracts **information patterns**.*

- **How it Works:** It ignores the file system entirely and scans the raw disk image for regular expressions (patterns). It looks for things like email addresses, credit card numbers, URLs, GPS coordinates, and EXIF metadata.
- **Why it is powerful:** It can find this text even if it is buried inside a compressed ZIP file, a fragmented document, or a dumped RAM image (`.mem`). It is highly multithreaded, making it incredibly fast.
- **The Command:**
    - `sudo bulk_extractor -o output_folder img.dd`
    - **`o`**: Output folder.
- **The Output:** Instead of giving you carved files, Bulk Extractor fills the output folder with `.txt` files (e.g., `email.txt`, `ccn.txt`, `domain.txt`) containing the extracted strings and their exact byte offset locations on the disk. You also get a `report.xml` summarizing the findings.

### **Magic Rescue (The Smart Carver)**

*Viva Tip: How is Magic Rescue different from Foremost/Scalpel? Foremost just blindly copies data between a header and footer. Magic Rescue uses "recipes" to actually invoke external programs (like `jpegtopnm`) to verify if the carved data is actually a valid file before saving it, resulting in far fewer "junk" files.*

- **The Recipes:**
    - Instead of one big `.conf` file, Magic Rescue uses a folder full of individual scripts called "recipes." These are usually located in `/usr/share/magicrescue/recipes/`.
    - If you look inside that folder, you will see files named `jpeg-exif`, `zip`, `avi`, etc.
- **The Command:**
    - *Lab Correction:* Your notes have `M o`. The standard output flag is `d`.
    - `sudo magicrescue -r zip -r jpeg-exif -d output_dir image.dd`
    - **`r <recipe>`**: Specifies the recipe to use. You can use multiple `r` flags in the same command to look for different file types simultaneously.
    - **`d <output_dir>`**: Specifies the directory where the successfully carved and validated files will be saved.

# Sleuthkit

The Sleuth Kit (TSK) is the absolute backbone of open-source digital forensics. While tools like Autopsy give you a nice GUI, Autopsy is actually just running these exact TSK commands under the hood. Mastering these CLI commands proves you actually understand how file systems work.

**There is no single command called `sleuthkit`.**

The Sleuth Kit (TSK) is actually the *name of the entire suite* of the command-line tools discussed below

### **The Master Boot Record (MBR) Deep Dive**

`dd if=image1.dd of=mbr count=1` (which grabs the first 512 bytes, or 1 sector) and view it with `xxd mbr`, you are looking at raw hex

⭐**MBR DOS PARTITION TABLE FORMAT**

![image.png](image.png)

- **Bytes 0 - 445:** Boot Code (Executable code to start the OS).
- **Bytes 446 - 509:** The Partition Table (64 bytes total). This holds exactly **4 partition entries**, each being **16 bytes** long.
- **Bytes 510 - 511:** Boot Signature (Always `55 AA` in hex. If it's missing, the drive isn't bootable or is corrupted).

**How to read a 16-byte Partition Entry (A Mini-Example):**

Isolate the first 16 bytes of the partition table from your `xxd` output. It looks like this:

`80 20 21 00 07 FE FF FF 3F 00 00 00 42 1A 06 00`

1. **Byte 0 (`80`):** Boot Indicator. `80` means active/bootable. `00` means inactive.
2. **Bytes 1-3 (`20 21 00`):** CHS (Cylinder-Head-Sector) Start Address. (Legacy, usually ignored today).
3. **Byte 4 (`07`):** **Partition Type.** Crucial! `07` means NTFS. `0B` or `0C` means FAT32. `83` is Linux.
4. **Bytes 5-7 (`FE FF FF`):** CHS End Address.
5. **Bytes 8-11 (`3F 00 00 00`):** **Starting LBA (Logical Block Address).** This is the most important part! It is written in *Little Endian* (backwards). You read it as `00 00 00 3F`, which is `63` in decimal. This tells you the partition starts exactly at Sector 63. (This is the number you give to `fls -o`!).
6. **Bytes 12-15 (`42 1A 06 00`):** Total Sectors in the partition (also Little Endian).

### **Volume Layer Analysis (Finding the Partitions)**

- **`img_stat image1.dd`**: Gives details about the image file itself (size, format).
- **`mmstat image1.dd`**: Tells you the volume system type (usually `dos` for MBR or `gpt` for modern drives).
- **`mmls image1.dd`**: **The most important command to run first.**
    - *Lab Use Case:* It lists the partition layout visually. You look under the "Start" column to find the sector offset where your data partitions begin (e.g., `8064`). You need this number for almost every other TSK command!

### **File System Layer Analysis**

- **`fsstat -o 8064 image1.dd`**: Once you have the offset from `mmls`, `fsstat` tells you everything about the file system inside that partition. It reveals the OEM name, sector sizes, cluster sizes, and the exact range of data blocks (sectors) where files are stored.

### **Data & Metadata Layer (Finding the Files)**

- **`fls -o 8064 image1.dd | less`**: Lists files and directories in that specific partition.
    - **`r/r`**: Regular file.
    - **`d/d`**: Directory.
    - : The holy grail of forensics. It denotes a **deleted file** that still has a metadata entry.
    - **The Inode Number:** Next to the file name, there is a number (e.g., `452`). This is the metadata address (Inode/MFT entry). You *must* write this down to extract the file.
- **`fls -d -o 8064 image1.dd`**: Filters the output to *only* show deleted files ().

### **Extraction & Recovery (Getting the Data Out)**

There are two ways to get files out of an image in TSK:

**Method A: `icat` (Extracting a single file by Inode)**

- **`icat -o 8064 image1.dd <Inode_Number> > hello.txt`**
    - *How it works:* You take the Inode number you found using `fls` and tell `icat` to dump the raw data blocks belonging to that Inode into a local file.
    - *Viva Tip:* If the output looks "weird" in the terminal, it's because you piped binary data (like a `.png` or compiled program) straight to the console instead of redirecting it into a file (`> filename.ext`).

**Method B: `tsk_recover` (Extracting directories or entire partitions)**

- **`tsk_recover -o 8064 image1.dd recovered_folder`**: This command parses the file system at offset 8064 and attempts to recover *all* deleted files it can find, placing them into a local directory named `recovered_folder`.

### **Deep File Metadata Analysis**

- **`istat -o 8064 image1.dd <Inode_Number>`**:
    - *Why you use it:* It prints out the deeply technical MAC times (Modified, Accessed, Created timestamps), the file's exact size, its ownership/permissions, and most importantly, it lists the exact physical data blocks (sectors) on the disk where the file's data fragments are currently sitting.

### **Lab Notes: Advanced Sleuth Kit (TSK) Operations**

### **1. Extracting Unallocated Space (`blkls`)**

- **Background:** File carvers (like Foremost or Scalpel) take a long time to run on a massive 1TB drive. But what if you only want to search for *deleted* files? The `blkls` (Block List) tool extracts **only** the unallocated space (the empty space where deleted files live) into a new, much smaller raw file.
- **The Command:**
    
    `blkls -o 8064 image1.dd > unallocated_space.raw`
    
- **How to use it:** Now, instead of running Foremost on `image1.dd`, you run it on `unallocated_space.raw`. It will run 10x faster and only pull up deleted data.
- *Viva Tip:* If the examiner asks, "How can we speed up file carving for deleted files?", mention `blkls`. It shows you understand data efficiency.

### **2. Finding Orphaned Files (`ils`)**

- **Background:** We used `fls` previously to list files. But `fls` relies on the directory structure. If a hacker deletes a file, and then deletes the folder that contained it, `fls` might not see it easily. `ils` (Inode List) bypasses folders entirely and lists raw Inodes (metadata entries), specifically focusing on unlinked (deleted) ones.
- **The Command:**
    
    `ils -o 8064 image1.dd | less`
    
- **The Output:** It will give you a list of deleted Inode numbers. You can then take any of those numbers and plug them straight into the `icat` command we used earlier to extract the file.

### **3. Inspecting Raw Data Blocks (`blkcat`)**

- **Background:** Sometimes a file is so corrupted that its Inode is gone, and standard extraction fails. `blkcat` lets you look at the raw physical sectors on the disk.
- **The Command:**
    
    `blkcat -o 8064 image1.dd <Block_Number> | hexdump -C | less`
    
- **How it works:** If you know a piece of data is sitting at disk block 5000, this command dumps the raw 1s and 0s of that specific block to your screen so you can inspect the hex signatures manually.

### **4. Creating a Forensic Timeline (`mactime`)**

- **Background:** This is the ultimate TSK reporting tool. Every file has MAC times (Modified, Accessed, Created timestamps). `mactime` takes all the files on a disk and builds a master chronological timeline. This is how you prove *when* a hacker executed a payload.
- **Step 1: Create the "Body File"** (A rough list of all files and their times):
    
    `fls -m / -r -o 8064 image1.dd > bodyfile.txt`
    
    *(The `-m /` formats it for mactime, and `-r` makes it recursive to search all folders).*
    
- **Step 2: Generate the Timeline:**
    
    `mactime -b bodyfile.txt -d > timeline.csv`
    
    *(The `-b` reads the body file, and `-d` formats the output nicely so you can open it in Excel/LibreOffice Calc).*
    
- *Viva Tip:* A "body file" is just an intermediate text file that holds raw MAC timestamp data before `mactime` formats it into a human-readable chronological timeline.
</aside>

# TestDisk

While Sleuth Kit is a collection of command-line utilities designed for deeply analyzing static forensic images, TestDisk is an interactive recovery utility primarily designed to fix partition tables and recover lost partitions on live or attached drives (though it handles undeletion very well too). They operate differently and serve different primary purposes, so keeping them separate will make your study guide much clearer.

### **Partition & File Recovery (TestDisk)**

**Core Purpose:** TestDisk is a powerful, interactive terminal application primarily designed to recover lost partitions and make non-booting disks bootable again. It is also highly effective at undeleting files from FAT, exFAT, NTFS, and ext2 file systems.

**1. Initializing and Device Selection**

- **The Command:** `sudo testdisk` (or `sudo testdisk image1.dd` to run it directly against an image file).
- **Log Creation:** The first prompt asks about creating a log file.
    - *Lab Practice:* Always select **`[ Create ]`**. This maintains a record of your actions, which is essential for forensic reporting.
- **Media Selection:** TestDisk will list all attached storage devices and loop devices (if you attached an image). Use the arrow keys to select your target drive and choose **`[Proceed]`**.
- **Partition Table Type:** TestDisk automatically detects the partition table type (usually `[Intel]` for standard PC MBR or `[EFI GPT]` for modern drives). *Viva Tip: Trust its auto-detection unless you specifically know it's wrong.*

**2. The Main Menu Options**

Once the drive is selected, you are presented with the main menu. The two most important options for lab evaluations are:

- **`[ Analyze ]`**: Used to search for lost partitions. If a partition table is corrupted, this option scans the disk structure, finds the lost partitions, and allows you to rewrite the partition table to restore access to the drive.
- **`[ Advanced ]`**: Used for file system utility tasks, such as undeleting files, creating an image of a specific partition, or extracting boot sectors.

**3. Recovering Deleted Files (Undelete)**

This is the most common use case in a lab setting:

1. **Navigate:** Select `[ Advanced ]`.
2. **Select Partition:** Use the up/down arrows to highlight the specific partition you want to search.
3. **Choose Action:** Use the left/right arrows at the bottom of the screen to select **`[ Undelete ]`** and press Enter.
4. **The File View:** TestDisk will display the directory structure.
    - *Visual Cue:* Deleted files are highlighted in **Red**.
5. **Selection and Extraction:**
    - Navigate to the deleted file.
    - Press **`:`** (colon) to select a file. It will turn **Green**. (You can select multiple files this way).
    - Press **`C`** (capital C) to copy the selected files.
6. **Destination Selection:** TestDisk will now show your local Linux file system (where you ran the command).
    - Navigate to your designated evidence or output folder.
    - Press **`C`** again to confirm the destination and paste the recovered files.

*Viva Tip: If the examiner asks, "Why use TestDisk instead of Scalpel?", explain that TestDisk recovers files based on the file system's metadata (retaining the original filename and folder structure), whereas Scalpel is a carver that ignores the file system and searches raw bytes, which loses original filenames.*

# WinHex

**Core Purpose:** WinHex is a universal hexadecimal editor. While tools like Autopsy give you a pretty view of files and folders, WinHex lets you look at the raw binary data (the 1s and 0s translated into Hex) of the entire disk. It is used for manual file carving, finding hidden data, and analyzing partition tables directly.

### **1. Loading Evidence (The Most Critical Step)**

- **The Process:** `File` -> `Open` (to open a single file) OR `Tools` -> `Open Disk` (to mount a physical drive or a logical partition).
- **Opening an Image (.dd / .e01):** `File` -> `Create/Open Image`.
- 🚨 **MAJOR VIVA TRAP:** WinHex is an *editor*. It can write to disks. Before you open *any* forensic image or drive, you must ensure WinHex is operating in **Read-Only Mode** (often checked in `Options` -> `General` -> `Read-Only`, or prompted when opening a physical disk). If the examiner sees you open an original evidence drive with write-access enabled, it is an instant fail for breaking the Chain of Custody.

### **2. File Recovery by Type (Data Carving)**

Your notes are spot-on here. This is WinHex's version of Foremost or Scalpel, built directly into the GUI.

- **The Process:** `Tools` -> `Disk Tools` -> `File Recovery by Type`.
- **How it Works:** Just like Foremost, it ignores the file system (FAT/NTFS) and scans the raw hex for file headers and footers (Magic Numbers).
- **The Customization:** When you click this, a menu pops up listing file types (JPEG, PDF, ZIP). This list is generated from a configuration file called `File Type Signatures.txt` (located in the WinHex installation folder).
    - *Lab Practice:* You can click "Signatures" in that pop-up menu to literally see the hex headers it is searching for.
    - *Viva Tip:* Why use WinHex for carving instead of Foremost? WinHex gives you granular, manual control. If an automated carver fails because a file header is slightly corrupted, you can manually search for the hex pattern in WinHex and extract the block of data yourself by highlighting it.

### **3. Navigating the Hex Workspace**

When you open an image, the screen splits into three main columns. You must know how to read them:

- **Left Column (Offsets):** The physical address (location) on the disk. Usually displayed in Hex (e.g., `00000000` is the start of the disk).
- **Middle Column (Hex Data):** The actual raw data, represented as two-character hex pairs (e.g., `FF D8 FF E0`).
- **Right Column (ASCII / Text Translation):** WinHex tries to translate the hex into readable human text. If you are looking at an email or a plain text document, you can actually read the contents right here, even if the file is "deleted."

### **4. Analyzing Partition Tables (MBR Analysis)**

Remember the Sleuth Kit MBR lesson we just did? WinHex is the best tool for visualizing it.

- If you open a physical drive image, scroll to the absolute top (Offset `00000000`).
- Look at the very end of the first sector (Offset `000001FE`).
- You will visibly see the hex characters **`55 AA`**.
- *Lab Use Case:* You can highlight the 16 bytes before that signature, and use WinHex's `View` -> `Template Manager` -> `Master Boot Record` to automatically decode the partition table, rather than doing the math by hand like we did in the terminal!

### **5. Advanced Capabilities**

- **Simultaneous Search:** `Search` -> `Simultaneous Search`. This is WinHex's version of Bulk Extractor. You can load a `.txt` file containing hundreds of keywords (names, drug terms, specific IP addresses), and WinHex will search the entire raw hex of the disk for all of them at the same time.
- **RAM Editor:** WinHex can open the live physical RAM (`Tools` -> `Open RAM`) of the machine it is running on to capture passwords or malware sitting in memory.

# **Autopsy**

Autopsy is the grand finale of this toolset. It is the premier open-source graphical interface for digital forensics, and under the hood, it is actually running all those Sleuth Kit (TSK) commands we just covered!

**Core Purpose:** Autopsy is a full end-to-end digital forensics platform used to ingest evidence, run automated analysis modules, visually browse file systems, and generate final case reports.

**1. Case Creation & Ingestion**

- **Starting a New Case:** You must define the Case Name, Base Directory (where Autopsy saves its database—*never* save this on the evidence drive!), and Case Number/Examiner details.
- **Adding Data Sources:** You can ingest raw images (`.dd`), E01 files, or even local logical drives.
- **The Ingest Modules:** This is the most critical part of setup. When you add a data source, Autopsy asks which "Ingest Modules" to run. These are automated scripts that analyze the data in the background while you work.

**2. Deep Dive: Hash Lookup & Databases**

- **Hash Lookup Module:** This automatically calculates the MD5/SHA-256 hash of every file on the image.
- **Custom Hash Databases:** You can import databases to automate finding or ignoring files:
    - **Known Good (Whitelisting):** You import the NSRL (National Software Reference Library) database. Autopsy will hide standard Windows OS files so you don't waste time investigating `explorer.exe`.
    - **Known Bad (Blacklisting):** You import databases of known malware or contraband hashes. If Autopsy sees a match, it immediately flags it in red.

**3. Deep Dive: MIME Types & Extension Mismatch (Highly Tested!)**

- **What is a Custom MIME Type?**
    - MIME (Multipurpose Internet Mail Extensions) is a standard way to classify file types (e.g., `image/jpeg` or `application/pdf`).
    - Autopsy determines a file's MIME type by looking at its raw hex signature (Magic Numbers), **not** its file extension.
    - *Elaboration:* If your lab involves a proprietary file type (like a custom encrypted database used by a suspect), you can add its custom hex signature to Autopsy so it automatically recognizes and categorizes it.
- **Extension Mismatch Detection Module:**
    - *How it works:* Suspects often try to hide data by changing the extension. For example, they might rename `stolen_passwords.zip` to `family_photo.jpg`.
    - *The Catch:* Autopsy scans the file, sees the MIME type is `application/zip`, but sees the extension is `.jpg`.
    - *The Result:* It places the file in the **"Extension Mismatch"** folder.
    - *Viva Tip:* "If I suspect a user hid an executable malware file by naming it `system_log.txt`, how do I find it quickly?" Answer: "Check the Extension Mismatch results in Autopsy."

**4. Keyword Searches & Indexing**

- **Keyword Search Module:** This builds a massive text index of the entire drive (including unallocated space).
- **Types of Searches:**
    - *Exact Match:* Searching for a specific name like "John Doe".
    - *Substring Match:* Searching for "crypto" to find "cryptocurrency", "cryptography", etc.
    - *Regular Expressions (Regex):* This is crucial. You don't search for a specific phone number; you search for the *pattern* of a phone number. Autopsy has built-in regex for Email Addresses, IP Addresses, and Credit Card numbers.

**5. Exploring the Evidence (The UI)**

Once ingestion is running, you navigate the data using the tree on the left side of the screen.

- **Views -> File Types:** Autopsy categorizes everything by extension and MIME type automatically.
- **Views -> Deleted Files:** Files carved from unallocated space or those with deleted metadata entries are easily viewed here.
- **The Content Viewer (Bottom Right):** When you click a file, this panel lets you view it as a picture, read its extracted text, or view its raw Hex (exactly like WinHex).

**6. Documentation & The "Notepad Timestamp"**

- **The Shortcut Answer:** If you are using standard Windows Notepad to keep a chronological log of your actions alongside Autopsy, press **`F5`**. This instantly inserts the current time and date into the text file.
- *Lab Best Practice Note:* While Notepad is okay for quick scratchpad notes, Autopsy has a built-in **Tagging system**. You should right-click important files, select "Tag File", and add a comment. When you are done, you click `Generate Report`, and Autopsy automatically builds a professional HTML or PDF report containing all your tagged files, their hashes, and your timestamps!

# Volitality

*Quick Lab Note:* The commands you noted (`--profile=`) indicate your professor is teaching **Volatility 2** (likely using the standalone Windows executable, `volatility_2.6_standalone.exe`). Volatility 3 is out now and doesn't require profiles, but Volatility 2 is still the gold standard for university evaluations.

### **Lab Notes: Volatile Memory Analysis (Volatility)**

**1. Initial Setup & Profiling**

- **The Command Structure:** `volatility -f cridex.vmem [plugin_name]`
- **`imageinfo`**: The mandatory first step. Volatility needs to know exactly what operating system the RAM dump came from to parse the memory structures correctly.
    - *Output:* It suggests a profile (e.g., `WinXPSP2x86`). You **must** append `-profile=WinXPSP2x86` to every subsequent command.

**2. Process Analysis (The "Viva Trap" Zone)**

This is where examiners will test you relentlessly. You must know the difference between these process plugins:

- **`pslist`**: Lists processes by walking the operating system's standard "doubly-linked list" (the `EPROCESS` block).
    - *The Catch:* If malware wants to hide, it simply unlinks itself from this list. `pslist` will **not** see hidden malware.
- **`psscan`**: Ignores the linked list and scans the raw memory bytes for the "Pool Tags" (signatures) of process structures. It **will** find hidden and recently terminated processes.
- **`psxview`**: *(Correction from your note "psxd")*. This is the ultimate cross-reference tool. It runs `pslist`, `psscan`, and several other checks, and puts them in a chart. If a process shows `False` under `pslist` but `True` under `psscan`, you have found a maliciously hidden process!
- **`pstree`**: Visually maps processes in a parent-child tree. Useful to see if `cmd.exe` was suspiciously spawned by a web browser.

**3. Network & Connection Analysis**

- **`connscan`**: Scans for active and previously terminated TCP connections.
- **`sockets`**: Finds listening sockets (ports that are open and waiting for incoming connections) across any protocol.
    - *Lab Practice:* Taking the foreign IP addresses found here and searching them on **MxToolbox** or **VirusTotal** is exactly how you confirm if the PC was communicating with a Command & Control (C2) server.

**4. Extraction & Deep Inspection**

Once you suspect a specific Process ID (PID), you need to rip it out of memory to analyze it.

- **`cmdline`**: Shows the exact command used to launch the process. *Did it run from `C:\Windows\System32` (normal) or `C:\Users\Temp\malware.exe` (bad)?*
- **`procdump -p 1484 -D <folder>`**: *(Correction from "procdum")*. Extracts the entire executable file from RAM and saves it to your destination folder so you can upload it to VirusTotal.
- **`dlllist -p 1640`**: Lists all Dynamic Link Libraries (DLLs) the process has loaded. Malware often injects malicious DLLs into legitimate processes (like `explorer.exe`).
- **`dlldump -p 1640 -b <base_address> -D <folder>`**: Dumps a specific, suspicious DLL out of memory using its base address.

**5. Registry & Timeline Analysis**

The registry is heavily cached in RAM. You can read it without needing the hard drive.

- **`hivescan`** -> **`hivelist`**: Finds the memory addresses of the loaded registry hives (like `SAM`, `SYSTEM`, `SOFTWARE`).
- **`printkey -o <offset> -K "Software\Microsoft\Windows\CurrentVersion\Run"`**: Prints the contents of a specific registry key. *Viva Tip:* The "Run" key is the most common place malware hides to ensure it starts when the computer boots.
- **`timeliner`**: Extracts every timestamp it can find in memory (process creation, network sockets, registry writes) and builds a massive chronological timeline of the attack.

### **The WannaCry Ransomware Case Study**

Your professor brought up a fantastic example. **WannaCry** (May 2017) was a devastating ransomware worm that encrypted hard drives and demanded Bitcoin. It was famous because it spread automatically using **EternalBlue**, a stolen NSA exploit that abused a vulnerability in the Windows SMB protocol (Port 445).

### **How to get the memory dump:**

Memory dumps of WannaCry are widely used in infosec training. You can find them legally on GitHub repositories dedicated to malware analysis. A very famous one is the **"MemLabs"** repository or the official **Volatility Foundation malware samples** page. (Search: *Volatility WannaCry memory dump sample*).

### **How you would analyze WannaCry in the lab:**

If your professor hands you a WannaCry RAM dump (`wannacry.vmem`), here is exactly what your Volatility workflow would look like:

1. **Find the Profile:** `vol.py -f wannacry.vmem imageinfo`
2. **Look for the Payload:** `vol.py -f wannacry.vmem --profile=Win7SP1x64 pslist`
    - *What you see:* You will likely spot extremely suspicious processes running, often named `@WanaDecryptor@.exe` or `tasksche.exe` (WannaCry uses this to achieve persistence).
3. **Detect the "Worm" Network Activity:** `vol.py -f wannacry.vmem --profile=Win7SP1x64 netscan`
    - *What you see:* Because WannaCry is a worm trying to infect other computers on the network, `netscan` will show hundreds of outbound connection attempts from the infected machine targeting **Port 445** on random external IP addresses. This is the smoking gun of EternalBlue.
4. **Find the Injected Code (`malfind`):** `vol.py -f wannacry.vmem --profile=Win7SP1x64 malfind`
    - *What it does:* `malfind` looks for memory sections marked with `PAGE_EXECUTE_READWRITE` (VAD tags) that do not map to a file on disk. This indicates code was maliciously injected straight into memory. WannaCry relies heavily on this.
5. **Dump and Verify:** `vol.py -f wannacry.vmem --profile=Win7SP1x64 procdump -p <PID_of_WanaDecryptor> -D ./`
    - *Final Step:* You dump the executable and check its hash on VirusTotal, which will immediately flag it as `Ransom.WannaCry`.</PID_of_WanaDecryptor>

`hping3` is affectionately known as a "packet crafter." While tools like `ping` just send basic ICMP requests, `hping3` lets you build custom TCP, UDP, and ICMP packets from scratch. Because of this, it is the ultimate tool for simulating network attacks in a lab environment.

### **Network Attacks & Defense (hping3, IDS, Honeypots)**

### **1. The TCP SYN Flood Attack (`hping3`)**

*Viva Tip: To explain a SYN Flood, you MUST mention the "TCP 3-Way Handshake" (SYN -> SYN-ACK -> ACK). In a SYN Flood, the attacker sends thousands of SYN packets. The server replies with SYN-ACK and allocates RAM to wait for the final ACK. The attacker never sends the ACK. The server's memory fills up with "half-open" connections until it crashes or stops responding to legitimate users.*

- **Lab Setup:** Run Wireshark in the background (`Capture` mode) while doing this. You will see a massive wall of red/black `TCP SYN` packets and no corresponding `ACK`s.
- **The Commands:**
    - `sudo hping3 -S -p 80 <ip_address>`: Sends standard TCP SYN (`S`) packets to port 80 (HTTP). *Note: `netstat -tuln` on the target machine will show these open ports.*
    - `sudo hping3 -S -c 100 -p 80 <ip_address>`: The `c 100` flag limits the attack to exactly 100 count/packets.
- **Resource Hogging (The Real DoS):**
    - `sudo hping3 -S -p 80 --flood <ip_address>`: The `-flood` flag sends packets as fast as possible, not waiting for replies. This is what actually overwhelms the target's CPU and bandwidth.
    - *Lab Variations:* You can use `-fast` (10 packets per second) or `-faster` (100 per second) for controlled bursts.

### **2. IP Spoofing & Attack Attribution**

Attackers rarely use their real IP address when launching a DoS attack.

- **The Commands:**
    - `sudo hping3 -S -p 80 -a 192.168.1.100 <target_ip>`: The `a` flag spoofs the source IP. The target thinks `192.168.1.100` is attacking them.
    - `sudo hping3 -S -p 80 --rand-source <target_ip>`: Randomizes the source IP for every single packet. This makes it a simulated Distributed Denial of Service (DDoS).
- 🚨 **MAJOR VIVA TRAP (How to catch the spoofer):** Your notes mention tracking them by MAC address. **Be careful here!**
    - **MAC Addresses:** You can *only* track an attacker by their MAC address if they are on the exact same local network (LAN/WiFi) as you. If they are attacking over the internet, the MAC address you see belongs to your ISP's router, not the attacker!
    - **TTL (Time to Live):** Your note about TTL is brilliant. If you see thousands of SYN packets coming from completely random IP addresses, but they *all* have a TTL of `53`, it proves they are all originating from the exact same machine and distance, exposing the `-rand-source` trick!

### **3. The Smurf Attack (ICMP Amplification)**

*Viva Tip: A Smurf attack is an "Amplification Attack." The attacker sends one packet, but the network multiplies it into hundreds of packets directed at the victim.*

- **How it Works:**
    1. The attacker spoofs their IP to match the **Victim's IP** (`60.0.0.14`).
    2. The attacker sends an ICMP Echo Request (Ping) to the **Network Broadcast Address** (`60.0.0.255`).
    3. Every single computer on the `60.0.0.x` network receives the ping.
    4. Every computer replies at the exact same time... but because the source was spoofed, all the replies hit the Victim (`14`), instantly overwhelming it.
- **The Command:** `sudo hping3 --icmp -a 60.0.0.14 60.0.0.255`
- **The Defense (System Configuration):**
    - Modern networks prevent this by telling routers to ignore broadcast pings.
    - Check status: `sudo sysctl net.ipv4.icmp_echo_ignore_broadcasts` (1 = Safe/Ignore, 0 = Vulnerable/Accept).
    - Fix it temporarily: `sudo sysctl -w net.ipv4.icmp_echo_ignore_broadcasts=1`
    - *Lab Note:* To make this fix permanent across reboots, you must add it to the `/etc/sysctl.conf` file.

### **4. Defensive Infrastructure (Honeypots & IDS)**

**Honeypots:** Decoy systems deployed alongside actual production servers. They contain no real data. Therefore, *any* connection to a honeypot is deemed malicious by default.

- **Cowrie:** A highly famous, medium-to-high interaction SSH and Telnet honeypot. It logs brute-force password attacks and actually provides the attacker with a fake Linux shell. It records every command the attacker types into the fake terminal so researchers can study their behavior.

**Intrusion Detection Systems (IDS):** The "burglar alarms" of the network. They sit quietly, copy all network traffic, and compare it against a database of known attack signatures (like the signature of an `hping3 --flood`).

- **Snort:** The grandfather of open-source IDS. Created by Cisco/Sourcefire. It uses a relatively simple rule language to drop or alert on malicious packets.
- **Suricata:** The modern rival to Snort. It is highly multi-threaded (much faster on modern multi-core CPUs) and natively understands complex application-layer protocols like HTTP and DNS out of the box.
